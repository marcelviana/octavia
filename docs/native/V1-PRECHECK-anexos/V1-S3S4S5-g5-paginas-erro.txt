$ o laço de páginas (apps/native/src/sync.ts:29-39)
  const paginas: ContentDTO[][] = []
  let page = 1
  let total = 0
  for (;;) {
    const r = await getContentPage(page)
    // D-d: a página que falhou viaja junto — o `sync fail` tinha `page=1`
    // hardcoded, e o aceite da N1-PR7 (§3.4) mediu a falha na página 2 sendo
    // reportada como 1. O catálogo define `page=<p>`.

    total = r.data.total
    if (!r.data.hasMore) break

$ e o _paginas do aceite.py, simulado com três tamanhos de biblioteca:
  content=  0  →  paginas=[0, 0]  len(paginas)=2
      página 1: hasMore = (1 < 2) = True
  content= 67  →  paginas=[40, 27]  len(paginas)=2
      página 1: hasMore = (1 < 2) = True
  content=140  →  paginas=[40, 100]  len(paginas)=2
      página 1: hasMore = (1 < 2) = True

VEREDITO: o `_paginas` do `aceite.py` devolve SEMPRE duas listas
(`content[:40]` e `content[40:]`), qualquer que seja o tamanho — inclusive zero.
Logo `hasMore` na página 1 é SEMPRE true, e o app pediu a página 2 porque o
servidor disse que havia mais. **O laço do app está correto**: ele para em
`if (!r.data.hasMore) break`. Contra um servidor real com N=0 (`hasMore:false`
na página 1) seriam 1 + 1 = 2 requests e `pages=1`, como o A4 prevê.
É artefato do APARATO; corrige-se no mock, não no app. O A4 não foi violado.
