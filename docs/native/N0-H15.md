## 1. Veredito

**H15-a — "usuário restaurado sem rede": VERDADEIRA** `[medido]`. Nas duas aberturas em modo avião (token fresco e token expirado) o app subiu com `OCTAVIA: auth uid=Pw3bxXZw0iT3WwyL7kxGtGJIJH83 src=restored` e **sem** `OCTAVIA: login-screen`; no controle negativo (`pm clear` com o avião ligado) veio **só** `OCTAVIA: login-screen` e nenhuma linha `auth uid=`.

**H15-b — "token disponível sem rede" (N0-H3): depende do estado do token** `[medido]`:
- token **fresco** (< 1 h): `getIdToken` devolve o token do cache; a request morre na rede (`sync-error fetch failed: java.net.UnknownHostException: Unable to resolve host "octavia.rocks"`), sem linha `api status=`.
- token **expirado** (> 1 h): `getIdToken` rejeita (`sync-error Firebase: Error (auth/network-request-failed).`) — o SDK tenta renovar e não há rede; **o usuário continua restaurado** (nenhum `auth-failure`, nenhum `login-screen`).

**O que isso significa para A5/T1-R19**: A5 ("modo avião com cache: kill + reopen, sem login") é atendível como escrito — o SDK restaura o usuário sem rede em ambos os estados do token, e o app não desloga quando a renovação falha (T1-R19: "se o SDK não conseguir renovar o token offline, o app **não** desloga: usa o cache"). O cache namespaced por `uid` (PRD §5) tem `uid` disponível offline. A tela 1 (N1) só precisa de token quando há rede e sync — exatamente o que H15-b mostra: sem rede, o erro fica na camada de rede única (T1-R37) e não na sessão.
